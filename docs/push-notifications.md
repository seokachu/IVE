# 푸시 알림 시스템 — 설계 정리 (포트폴리오/면접용)

하이브리드 앱([seokachu/ive-app](https://github.com/seokachu/ive-app)) 사용자에게
댓글/답글 푸시 알림을 보내는 시스템의 아키텍처와 설계 결정 기록.

## 전체 아키텍처

```
[Expo 앱]                      [Next.js 웹 (Vercel)]                [Supabase]
푸시 토큰 발급                                                      push_tokens 테이블
  │ WebView에 주입                                                    (RLS: 본인만 쓰기)
  └────────────────▶ PushTokenSync가 로그인 사용자와 ──────────────▶ upsert
                     연결해 저장

[댓글 작성] ──▶ useAddComment 성공 ──▶ POST /api/push/comment (fire-and-forget)
                                        │ 1. 쿠키 세션으로 작성자 본인 검증
                                        │ 2. 수신자 계산 (글 작성자 + 원댓글 작성자)
                                        │ 3. service role로 수신자 토큰 조회
                                        ▼
                              Expo Push API ──▶ FCM(Android)/APNs(iOS) ──▶ 기기
                                        │
                                        └ DeviceNotRegistered 응답 시 토큰 삭제

[앱 수신] ──▶ 알림 탭 ──▶ data.url의 게시글로 WebView 이동 (콜드 스타트 대응)
```

## 핵심 설계 결정

### 1. 비밀키는 서버에만, 앱은 토큰 전달만

- `service_role` 키(모든 RLS를 우회하는 관리자 키)는 **Vercel 서버 환경변수에만** 존재.
- 앱 번들은 사용자 기기에 배포되므로 어떤 비밀도 넣지 않는다.
  앱의 역할은 "토큰을 발급받아 WebView 전역(`window.__IVE_PUSH__`)으로 전달"까지.
- 토큰을 사용자와 연결하는 것은 **이미 인증 체계를 갖춘 웹**이 담당 —
  Supabase 세션·RLS를 그대로 재사용하므로 앱에 별도 인증을 구현할 필요가 없다.

### 2. 발송 권한 검증은 서버에서

- `/api/push/comment`는 클라이언트가 보낸 `boardId/commentId`를 신뢰하지 않는다.
  쿠키 세션으로 사용자를 확인하고, **해당 댓글이 실제 그 사용자가 방금 작성한
  것인지 DB에서 재검증**한 뒤에만 발송한다.
- 이 검증이 없으면 로그인한 아무나 API를 반복 호출해 다른 사용자에게
  스팸 푸시를 보낼 수 있다.

### 3. 수신자 결정 로직 (알림 관련성 우선순위)

주요 서비스들의 공통 패턴: **나에게 직접 온 반응**(내 글의 댓글, 내 댓글의 답글)이
가장 관련성 높은 알림이다. 이에 따라:

- 일반 댓글 → **글 작성자**에게
- 대댓글 → **글 작성자 + 원댓글 작성자**에게
- 게시글 좋아요 → **글 작성자**에게 (추가일 때만, 취소는 미발송)
- **본인 제외**: 자기 글/댓글에 자기가 만든 이벤트는 발송하지 않음
- **중복 제거**: 글 작성자 = 원댓글 작성자면 더 구체적인 "답글" 알림 하나만
  (Map<userId, type>으로 수신자별 알림 타입을 결정)
- 알려진 트레이드오프: 좋아요를 껐다 켜면 재발송된다. 발송 이력 테이블로
  중복을 막을 수 있으나 현재 규모에서는 단순함을 우선했다.

### 4. 알림 피로(notification fatigue) 대응

- 알림을 줄이는 방식이 아니라 **묶고, 걸러서** 대응:
  OS 레벨 그룹핑(Android 자동), 셀프 알림 제외, 수신자 중복 제거.
- **수신 설정**: 마이페이지에 푸시 알림 on/off 토글 제공.
  `push_tokens.enabled` 컬럼(기본 true)으로 관리하고 발송 시 서버가 필터링 —
  클라이언트가 아닌 발송 지점에서 거르므로 설정이 늦게 반영될 틈이 없다.
- 다음 단계 후보: 알림 종류별 세분화(댓글/답글/좋아요 개별 설정).

### 5. fire-and-forget 발송

- 댓글 작성 UX는 푸시 발송 성공 여부와 무관해야 한다.
  발송 API 호출은 `catch(() => {})`로 감싸 실패해도 댓글 흐름에 영향이 없다.
- 트레이드오프: 발송 실패를 사용자는 모른다 → 알림은 best-effort 성격이므로 허용.

### 6. 토큰 수명 관리

- 토큰은 `token`을 PK로 upsert — 기기당 1행, 계정 전환 시 자동으로 새 사용자에 연결.
- Expo 발송 응답의 `DeviceNotRegistered`(앱 삭제 등)를 감지해 즉시 삭제 —
  죽은 토큰이 쌓이는 것을 방지.

### 7. 내용 미리보기와 프라이버시

- 알림 제목은 맥락("~글에 새 댓글" / "내 댓글에 답글"), 본문은 내용
  (`작성자: 댓글 미리보기...`, 40자 잘라내기) — 인스타그램/유튜브와 같은 패턴.
  내용이 보여야 사용자가 지금 열어볼지 판단할 수 있다.
- 잠금화면에서 내용을 가릴지는 앱이 아닌 **OS의 민감한 알림 설정에 위임**한다.
  앱이 선제적으로 숨기면 오히려 알림의 정보 가치가 사라진다.

### 8. 왜 Firebase(FCM)인가

- Android 푸시의 공식 전달 채널은 FCM뿐이다. 어떤 푸시 서비스를 쓰든
  Android 기기로의 최종 전달은 FCM을 거친다 (iOS는 APNs).
- Expo Push는 FCM/APNs를 단일 API로 통합해주는 레이어 —
  서버는 플랫폼 구분 없이 토큰 배열만 넘기면 된다.
- Firebase의 다른 기능(DB·인증)은 쓰지 않는다. 데이터는 Supabase 유지.

## 예상 면접 질문과 답변 포인트

**Q. 왜 웹뷰 하이브리드인데 푸시가 되나?**
→ 푸시는 네이티브 레이어(Expo)가 받고, 알림 탭 시 `data.url`을 WebView에 주입해
웹 페이지로 라우팅한다. 네이티브와 웹의 역할 분리가 이 프로젝트의 핵심 구조.

**Q. 토큰과 사용자는 어떻게 연결했나?**
→ 앱은 로그인 상태를 모른다. 토큰을 WebView 전역에 주입하면, 로그인 세션을
가진 웹이 자기 사용자 ID와 연결해 저장한다. 인증을 한 곳(웹)으로 모은 설계.

**Q. 아무나 API를 호출해 푸시를 보낼 수 있지 않나?**
→ 쿠키 세션 인증 + "그 댓글을 방금 그 사용자가 썼는지" DB 재검증.
클라이언트 입력은 검증 전까지 신뢰하지 않는다.

**Q. 대댓글 알림에서 신경 쓴 부분은?**
→ 수신자 중복(글 작성자 = 원댓글 작성자)과 셀프 알림 제외.
Map으로 수신자별 알림 타입을 계산해 한 사람에게는 가장 구체적인 알림 하나만 간다.

**Q. 푸시 발송이 실패하면?**
→ 댓글 UX와 분리된 fire-and-forget. 만료 토큰은 발송 응답에서 감지해 자동 정리.

**Q. 확장한다면?**
→ 좋아요 알림 등 이벤트 추가는 같은 패턴 재사용. 트래픽이 커지면 DB Webhook +
Edge Function으로 발송을 웹 요청 경로에서 분리(비동기화)하는 것이 다음 단계.
